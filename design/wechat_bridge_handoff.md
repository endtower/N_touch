## 目标与当前进度

为 N_Touch 接入个人微信，先独立验证 Windows 桌面自动化能否完成消息读取与发送。用户需要继续使用自己的电脑，最关注微信能否被遮挡或最小化后运行，以及操作是否抢占键盘、鼠标和窗口焦点。

用户已同意尝试桌面自动化，也在考虑借助 AI 编写自己的微信操作层。目前只完成方案讨论，没有安装 wxauto、探测微信控件或执行微信收发测试。

建议新工作区为 `E:\ABYSS\WeChatBridge`。这只是建议路径，尚未创建，也尚未切换工作区。现有工作区为 `E:\ABYSS\N_Touch`，包含大量已有改动，不应在试验中覆盖或清理。

## 用户意图与范围

- 优先解决微信操作层，暂不接入 N_Touch 的完整 AI 流程。
- 目标是个人微信的私聊、群聊，而非企业微信或微信客服入口。
- 优先探索后台读取、后台发送，不默认采用必须抢焦点的点击脚本。
- 可以评估自研，不要求依赖 wxauto，也不要求完整重写 wxauto。
- 第一阶段只处理指定会话的纯文字；图片、语音、文件、引用和合并转发随后再考虑。
- 本次方向是桌面自动化，不开展 DLL 注入或协议逆向。
- 用户拥有树莓派 4（4 GB），但是否将其他后台组件搬过去尚未决定。

## 已查证的信息

以下资料于 2026-10-11 查阅，后续选型应再次检查版本兼容情况。

1. wxauto 基于 Windows UI Automation 操作已登录的桌面应用，提供微信客户端适配。它不是微信官方 API。
   - https://docs.wxauto.org/
2. wxauto 有公开源码仓库，仓库随附 Apache-2.0 许可证；公开 README 标注微信 3.9.X。不能据此推断适配用户当前微信，也不能把最新产品文档的全部能力视为开源版已有功能。
   - https://github.com/cluic/wxauto
   - https://github.com/cluic/wxauto/blob/main/LICENSE
3. 当前产品区分 wxauto 开源组件与 wxautox Plus 商业工具，使用现成代码或产品前需核对对应版本、许可和功能。
   - https://docs.wxauto.org/agreement.html
   - https://docs.wxauto.org/legal/commercial-license.html
4. 当前文档包含指定聊天监听接口 `AddListenChat`，返回监听子窗口实例；监听使用守护线程，需要保持主程序存活。接口回调不等于微信服务器提供了可靠消息订阅。
   - https://docs.wxauto.org/docs/class/WeChat.html
5. wxauto 文档明确仅支持 Windows，不支持 Linux/macOS。不能在树莓派常用的 Linux 系统上直接运行该库。
   - https://docs.wxauto.org/docs/issues.html
6. Windows UI Automation 提供读取文本、设置控件值、执行按钮动作等能力，但具体控件是否支持由目标应用的实现决定。
   - https://learn.microsoft.com/en-us/windows/win32/winauto/uiauto-controlpatternsoverview

## 尚未确认的关键条件

不要把以下事项作为已验证能力，也不要承诺“后台稳定运行”“绝不漏消息”或具体漏消息比例：

- 用户的 Windows 版本、微信版本和客户端架构。
- 当前微信是否暴露足够的消息控件、输入框和发送动作。
- 微信被遮挡、最小化、关闭到托盘时，控件是否仍可读和可操作。
- 能否发送文字而不激活微信、不移动鼠标、不占用系统剪贴板。
- 是否必须打开独立聊天子窗口，以及这些子窗口的后台行为。
- UI 消息标识是否稳定，能否可靠区分连续相同文字和自己发出的消息。
- 密集消息、窗口重建、断线重连后是否能补读缺失内容。
- 锁屏、远程桌面断开后的行为。注销或睡眠期间不能依靠当前交互桌面持续操作。

“程序隐藏运行”“微信被遮挡”“微信最小化”“关闭到托盘”应分别测试，不能混为同一种后台状态。

## 建议实施顺序

### 1. 创建独立试验环境

确认新目录后创建工作区，检查该目录的 AGENTS.md 和已有文件。记录 Python、Windows、微信版本。依赖先装入独立环境，不修改 N_Touch 的运行环境。

先使用 Windows UI Automation 的公开能力做最小探测；可以评估适当的基础库，避免为了少量收发功能复制整套微信机器人框架。

### 2. 只读探测

定位微信窗口，列出相关控件的类型、名称和可用操作模式。报告尽量只包含结构，避免导出无关好友和聊天正文。

在指定会话依次验证正常显示、其他窗口遮挡、最小化、托盘状态。记录窗口是否被恢复或激活、消息是否可见、读取耗时和错误原因。此阶段不点击发送、不修改草稿。

### 3. 文件传输助手发送测试

此前提出的初始测试范围为“文件传输助手”，不要自行扩展到真实联系人或群聊。测试前确认用户已经正常登录，并记录发送前的窗口焦点及草稿状态。

优先尝试控件提供的设置文本和执行动作能力；若必须使用前台输入，应明确记录，不能静默切换成抢焦点方案。

发送一条带唯一测试标记的文字，随后检查聊天里是否出现对应的自己发言。区分：已执行输入、点击/执行发送、在界面观察到发出、对端收到。文件传输助手界面回显不能证明所有场景的对端送达。

### 4. 新消息监听与异常测试

用户确定测试会话后，再验证真实入站消息。监听回调只做读取、入队和持久化，不等待 LLM。先限定少量会话。

验证连续消息、连续重复文字、长文本、自己发出的消息、聊天窗口关闭后重建、微信重启和程序重启。通过重叠读取最近消息减少漏读，但不要用“发送者＋文字”作为唯一去重键，也不要将 UI RuntimeId 默认视为永久消息 ID。

恢复后仍无法确认完整性的时段要标记出来。发送结果不明确时，不直接自动重发。

### 5. 根据证据决定运行方式

- 如果被遮挡时能稳定读写且不抢焦点，继续本机后台方案。
- 如果可以后台读但只能前台发，报告限制，再决定发送排队或隔离桌面方案。
- 如果必须前台操作，评估 Windows 虚拟机或独立 Windows 设备。最小化宿主上的虚拟机查看窗口，与最小化虚拟机内部微信不是同一件事；保持虚拟机运行、内部登录与不睡眠的条件仍需验证。
- 树莓派可以另行评估队列、存储或后台服务，不能据此取代 Windows 微信操作端。N_Touch 是否能在 ARM/Linux 上运行尚未审查。

## 未来与 N_Touch 对接

建议保持独立桥接进程，通过本地接口交付消息与发送请求。桥接负责微信窗口操作和状态；N_Touch 负责消息存储、AI 决策及发言限制。

现有项目已经有 `adapt/protocol.py`、`adapt/manager.py` 和 `adapt/router.py`。发送工具位于 `brain/base/common_ways/tool_conversation.py`，其底层发送目前仍指定 `platform="qq"`，目标会话主要采用 `private_xxx / group_xxx`。

正式接入时需要将平台纳入会话身份及路由，避免 QQ 与微信同类 ID 混淆。不要只加一个微信 Channel 就认为对接完成。现有发言限制可共用，但应按平台和目标会话隔离统计。

本轮讨论之前已经在 N_Touch 实现了文字发言限制，独立微信试验暂不修改它：

- 每个 LLM 执行轮次最多调用一次文字发送工具；一次最多三条换行分段。
- 超出的分段不发送；重复工具调用不执行，并在 tool response 中返回警告和未发送内容。
- 最近 60 秒实际输出的非空白字符达到 150/300，且没有用户新回复时，下一轮最多 2/1 条。
- 触发限制后才通过 tool response 提示，附带 120/60 字的软长度建议。

## 新工作区起步任务

开发 Windows 微信桌面自动化原型。先探测当前微信版本与 UI Automation 控件，验证窗口被遮挡、最小化时能否读取消息，以及能否不抢焦点发送文字。先做只读探测，发送测试仅使用文件传输助手。暂不接入 N_Touch，不使用 DLL 注入。记录实际结果与限制，再决定是否开发监听和完整桥接。优先支持用户继续正常使用电脑，不把后台收发能力当成已知条件。
